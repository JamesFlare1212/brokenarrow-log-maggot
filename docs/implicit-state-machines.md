# Implicit state machine inventory

This inventory began with baseline `f3e95b2c` (BARadar `4.5.9`) and is updated
for the nine repairs in the [risk audit and fixes](state-machine-risk-audit.md).
It describes the current workflow decomposition. The repair ledger records
original failing interleavings, current ownership contracts, and normal regression
coverage; it does not certify every possible interleaving.

## Scope and terminology

A workflow belongs in this inventory when it remembers previous events or work
and that memory changes which subsequent events, results, or side effects are
accepted. The state can live in booleans, nullable objects, promises, maps, refs,
timers, files, or SQLite rows. Most entries are extended state machines: their
control states are finite, but their context includes IDs, timestamps, and queues.

- **Implicit** means the control state is inferred from several values or from
  the current point in an asynchronous procedure.
- **Hybrid** means a public `phase`, `status`, or reducer exists, but additional
  context determines valid transitions. Having a status field does not make the
  complete protocol explicit.
- **Persistent** means some state survives application restarts. This is a
  storage property, not a separate kind of control flow.

The main inventory has **66 workflow and subworkflow entries**, grouped by
responsibility. This is a decomposition, not a claim that there are 66 independent
finite automata: several entries describe cooperating parts of one feature.
Small command controls, presentation state, development tooling, and synchronous
parsers are listed separately below so they do not disappear behind that count.

The scope covers repository-owned runtime code in `apps/desktop/src`,
`apps/server/src`, `apps/web/src`, and relevant contracts/shared functions.
Dependencies, generated bundles, test doubles, release/build/smoke scripts, and
design prototypes are outside the application inventory. Library-owned Radix,
Electron, SQLite, WebCodecs, Mediabunny, and native media-element state machines
are not expanded. No application use of XState or another statechart library was
found. Pure calculations and ordinary form values alone are not treated as
workflow state machines.

State names in the tables are reconstructed descriptions unless shown as code
literals. Arrows describe important paths, not a formal exhaustive transition
table. Source links point to the implementation; the risk ledger records repair details.

## Cross-module protocols and modeling priorities

The most valuable boundaries to make explicit, if refactoring is requested, are:

1. **Recording:** R01/R02/R03/R04 plus N07 and F06. `phase` alone omits ownership,
   startup cancellation, tail-write acceptance, finalization, and discard. Capture
   identity and output ownership must survive every awaited boundary.
2. **Service/update shutdown:** L01/L02/U02. Distinguish admission closed,
   dependencies draining, prepared installer handoff, recovery, and disposed.
   Preserve the deferred install RPC boundary to avoid self-deadlock.
3. **Log ingestion:** G01/G02/G03/G06/G08. Recovery provenance is orthogonal to
   game phase and must be retained across partial lines and late metadata.
4. **Request ownership:** L03/L04/N02/N05/F01/F03. Global revision, session
   generation, per-request identity, and capture token solve different ordering
   problems. A result being newer globally does not establish that it still
   belongs to the current target. Logical cancellation is distinct from aborting
   shared transport work.
5. **Settings/moving files:** F02/F04/F06/D10. One provider queue retains staged
   directory text, failed patches, and preparation across tabs. Per-field freshness
   protects newer events. A persistent verified-copy journal models the
   copy-committed/source-pending deletion retry.
6. **Persistent once-only behavior:** G08/D03/D04/D08/U03/A05/A06. A reset or
   restart does not erase checkpoints, deletion markers, imported-file markers,
   reminder pairs, installer attempts, or delivered-version observations.

The follow-up [risk audit and fixes](state-machine-risk-audit.md) records the
nine repairs and promoted regressions. N06/N07 one-attempt admission and
capture/migration integration remain separate static concerns. Existing request
generations protect straightforward stale-thumbnail replacement.
